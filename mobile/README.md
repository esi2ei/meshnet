# MeshNet Android app

The Android APK now presents the same React/Vite dashboard as the web project. Gradle builds the dashboard and packages it into the APK under `web/`; the app serves it through AndroidX WebViewAssetLoader from the virtual `https://appassets.androidplatform.net/assets/web/index.html` origin; requests are fulfilled from the APK without contacting a server. A restricted JavaScript bridge connects the bundled UI to native Android BLE, Wi-Fi, messaging, file and voice APIs. Each BLE-capable phone starts both the GATT server/peripheral path and the scanner/GATT client path, allowing every participating phone to originate and receive traffic. If BLE advertising or GATT server startup is unavailable, the mesh session remains alive and can use Wi-Fi Aware or user-started Wi-Fi Direct when the device supports those radios. No app can guarantee connectivity on hardware lacking every supported local transport. The dashboard graph is populated from ready MeshNet GATT channels plus established Wi-Fi Direct and Wi-Fi Aware data-channel connections. Discovery results are never treated as connected peers. The foreground service maintains a shared peer registry keyed by transport and remote address; disconnecting one transport removes only that transport's link. The topology separates current direct radio links from observed multi-hop paths reconstructed from group-key-authenticated frame hop histories. Route observations expire after 30 minutes and are explicitly labeled as historical observations, not proof that every hop is currently online. Native event history is sourced from Android service callbacks.

The source browser includes frontend, Android, instrumentation-test, Rust/Anchor, Gradle, workflow, script, configuration and documentation text files captured from the local repository at build time; generated outputs, dependency caches and binary assets are excluded. See [the architecture map](../docs/ARCHITECTURE.md) for module ownership and peer lifecycle rules. The packaged dashboard is offline-first: relative asset URLs, local system fonts, no remote avatar images, blocked external navigation, and a Content Security Policy that denies network requests from the WebView. Optional Solana Mobile Wallet Adapter authorization and user-approved native SOL transfers on Devnet are separate opt-in integrations; they require internet and are not required by local messaging or the offline wallet. No cloud messaging, telemetry, or automatic uploads are provided.

**Offline wallet (local-unit prototype):** each installation creates a device-bound P-256 signing key in Android Keystore and derives a local wallet address from its public key. The sender persists an outgoing voucher record before transmission, signs a `MESH-LOCAL-UNIT` voucher, and sends bounded chunks through the encrypted mesh. The receiver persists incomplete chunks in private app storage so service/process recreation can resume reassembly; completed envelopes are replayed through receipt processing after restart. The recipient verifies the signature and recipient binding, atomically persists the receipt/replay ID, then signs an application-level acknowledgement with its own device key. The sender verifies that acknowledgement against the exact queued voucher and persists the `RECEIVED` state. The signed voucher itself is retained in the sender's private outgoing journal; the dashboard exposes an explicit retry action for unconfirmed vouchers, reusing the same voucher ID so the recipient can safely return its already-persisted receipt acknowledgement after a lost response or interrupted session. This is a verifiable offline receipt flow, not a money ledger: there is no issuance, spendable balance, authoritative ledger, global double-spend prevention, fiat/crypto backing, blockchain settlement, or guaranteed finality. A lost acknowledgement leaves the transfer unconfirmed; it must never be presented as settled. Do not use it for money or valuable assets.

## Implemented

- Bundled React/Vite dashboard hosted from APK assets, with a local-only WebView origin and a narrow `@JavascriptInterface` bridge. The bridge exposes only the user actions needed by the dashboard; non-local WebView navigation and content access are denied.
- Native device controls in the bundled dashboard: start/stop BLE mesh, encrypted text queueing, file selection and export, voice-note recording/playback, opt-in live voice, Wi-Fi Aware and Wi-Fi Direct actions, an offline signed local-unit wallet transfer prototype, and optional Devnet wallet authorization/native SOL transfer.
- Persisted online-integration switch, defaulting to off. BLE and local peer-to-peer features work without enabling it. WebView content has no network connection permission through its Content Security Policy.
- BLE service UUID advertising, filtered scanning, GATT server/client connections, and reconnect discovery.
- User-controlled Wi-Fi Direct group creation, peer discovery, explicit MAC-address connection, and length-prefixed TCP frame transport; optional Wi-Fi Aware publish/subscribe discovery with PSK-protected TCP data-path negotiation on supported hardware. BLE remains active when Wi-Fi Direct is unavailable or its optional permission is denied; Wi-Fi Aware is the default high-throughput peer transport when available.
- Adaptive per-peer BLE congestion handling: queue admission tightens after write failures, exponential backoff is applied, and durable outbox replay resumes when the backoff expires.
- Ingress-aware relay suppression and destination-aware text routing: broadcast frames are not immediately sent back to their ingress peer. Directed frames carry an authenticated destination, learn reverse next-hop candidates from verified message origins and the actual ingress peer, try up to three alternatives, and fall back to bounded flooding when no route is known or usable. Direct writes are transport-qualified across BLE/GATT, Wi-Fi Direct and Wi-Fi Aware. Next-hop ranking combines hop distance with smoothed per-peer measurements (BLE RSSI, targeted-write acceptance/failure, and write-completion latency where available). Measurements are bounded and decay toward neutral after five minutes without fresh observations; they are not end-to-end RTT/throughput or proof that a cached peer remains online.
- GATT frame fragmentation sized to the negotiated MTU, ordered per-peer writes, bounded write queues, bounded reassembly buffers, and reassembly expiry. Frames are capped at 960 bytes and fragmented according to the negotiated GATT MTU. Write queues and reassembly buffers are bounded; compact 128-bit node IDs keep routing metadata within the frame budget.
- Protocol v6 uses AES-256-GCM encrypted text, receipt, and non-durable EPHEMERAL frames. Authenticated frame metadata includes kind, origin, optional destination, frame ID, timestamp, receipt target, TTL, route history, and the sender's device public key, plaintext digest, and P-256 signature. Receivers verify the origin-key binding and signed plaintext digest. Participating devices must run the same protocol version; migration clears incompatible queued ciphertext and replay state. Group payload encryption still uses a shared group key: device-origin signatures do not provide per-device session encryption, forward secrecy, ratcheting, or secure group-key rotation. Relays re-encrypt after changing authenticated route metadata.
- Receipt policy: the router rejects ACKs by default unless an application validator approves the signer and intended destination. Directed messages can be retired only after the receipt origin matches the stored destination. Group-broadcast ACKs remain fail-closed until authenticated recipient-roster, protocol-v7, router/outbox and UI integration is complete; no every-member or offline-member delivery guarantee is claimed.
- Persistent SQLite outbox (6,000-frame cap, 24-hour retention) and persistent receiver replay-ID cache (bounded to 8,192 IDs).
- Streaming bounded-file transfer over the same encrypted group-routed message channel: 10 MiB maximum per file, 48-byte chunks, 16-chunk bounded send windows, receiver-driven contiguous checkpoints, compact durable resume metadata, batched file sync/checkpoint every eight received chunks, retries after lost windows, stable transfer IDs for identical content/name, up to two active incoming files, and streaming SHA-256 verification before a file is finalized in app-private storage. The sender file is streamed rather than loaded into one whole-file byte array. A terminal completion ACK is emitted only after digest verification, promotion to the final private file, and durable publication of its deduplication marker; intermediate window ACKs only confirm checkpointed chunks. The inbox retains at most 50 completed files / 100 MiB and removes the oldest completed file when the quota is reached. The UI reports acknowledged bytes, percentage and chunk progress, average acknowledged throughput, and inbound checkpoint progress. The app targets Android 16 (API 36); its root layout applies system-bar, display-cutout, and IME insets so interactive controls remain within safe areas on edge-to-edge displays. Use **Send file**, **Cancel outgoing file transfer**, and **Save received file** in the Android app.
- Short voice notes are recorded locally as AAC/M4A (up to 7 seconds) and sent through encrypted file transfer. A separate opt-in live group voice prototype uses 8 kHz mono AMR-NB packets at 20 ms intervals inside encrypted v6 EPHEMERAL frames, per-speaker jitter queues/decoders, and a bounded audio mixer. It requests transient exclusive Android audio focus, switches to communication mode while active, restores the prior audio mode/speaker route, and ends the call on permanent or transient focus loss. Live audio bypasses the durable outbox and has no delivery ACK; incoming calls do not open the microphone. Users must explicitly start or join, and microphone permission is requested only for recording or joining/starting a call. AMR-NB codec availability, echo behavior, latency, and audio quality have not been validated on physical devices.
- User-started Android connected-device foreground service with an ongoing notification.
- User-initiated Solana Mobile Wallet Adapter authorization/deauthorization and native SOL transfers on Devnet. The app builds a bounded legacy SystemProgram transfer, asks the connected wallet to sign and submit it, then reads the returned signature status from Devnet RPC. The authorized public address and MWA token are persisted as AES-GCM ciphertext protected by an Android Keystore key. Mainnet, SPL-token and escrow transfers are not implemented.
- Runtime Bluetooth and notification permission requests for supported Android versions.

## Build locally (no CI)

Requirements: Node.js 22.12+, npm, JDK 17, Android SDK Platform 36, Android Gradle Plugin 8.13.2, Kotlin Gradle Plugin 2.4.21, and Gradle 8.13. From the repository root, install the web dependencies, then build Android. The Android Gradle preBuild task runs the Vite production build and bundles its output:

Google Play has required new apps and updates to target Android 16 (API 36) or higher since August 31, 2026. This branch is configured for API 36; confirm API-level behavior and device compatibility in your manual test pass.

    npm install
    cd mobile
    gradle :app:assembleDebug

On Windows PowerShell, run the helper from the repository root. It checks Node.js 22+, npm, JDK/Gradle/Android SDK prerequisites, installs dashboard dependencies without writing a lockfile, verifies the APK signature when `apksigner` is installed, and copies the result to `mobile/dist/MeshNet-debug.apk`:

    powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\mobile\Build-DebugApk.ps1

Instrumented protocol and SQLite tests are included under `app/src/androidTest`. Run them locally on a connected Android device or emulator with:

    gradle connectedDebugAndroidTest

The Gradle build runs the web production build as part of preBuild; these commands do not invoke GitHub Actions. The PowerShell helper accepts `-RunConnectedTests` to run the instrumentation suite after creating the debug APK. A successful debug APK build does not certify physical-device interoperability or production security.

Install the debug APK on at least two BLE-capable Android phones. On each phone, enter the same high-entropy passphrase (at least 24 characters), grant Bluetooth and notification permissions, and start the mesh. A blank passphrase field reuses the locally saved credential. Use “Forget saved group credentials” to delete it from that device.

For Wi-Fi Direct, start the mesh on both devices. On one device choose **Create Wi-Fi Direct group**. On the other choose **Discover Wi-Fi Direct peers**, copy the discovered device address from the log, enter it, and choose **Connect to Wi-Fi Direct peer**. The group owner hosts the local TCP socket; the client connects to it. Wi-Fi Direct is user-triggered and does not auto-connect to discovered devices. Wi-Fi Aware discovery starts automatically on Android 10+ when supported. To avoid radio coexistence conflicts, choosing Wi-Fi Direct stops Wi-Fi Aware; use “Switch back to Wi-Fi Aware” to stop Wi-Fi Direct and resume Aware discovery.

For a multi-hop BLE check, use three phones with each device within BLE range of at least one neighbor, then move the origin and destination out of direct range while keeping the relay in range. Verify the receiver log shows the message and hop count.



## GitHub Actions validation and APK artifact

Pull requests targeting `main` automatically run MeshNet CI. The web job installs dependencies on Node 22, runs `npm run lint` and `npm run build`, and uploads the tested dashboard bundle. The Android job downloads that bundle, builds the debug APK with JDK 17, Gradle 8.13, and Android SDK Platform 36, then verifies the APK signature and SHA-256 checksum. Pull-request runs also execute the 22-class focused Android regression suite on an API 36 Google APIs emulator.

The complete (non-focused) Android instrumentation suite is opt-in through `workflow_dispatch` with `run_android_instrumentation=true`. A manual dispatch retains a downloadable debug APK and test reports; routine successful PR runs do not retain a debug APK except for the repository-owned `release/trial-apk` PR. The workflow does not run on ordinary push events. Failed Android jobs upload diagnostic logs.

Download the APK from the successful workflow run's **Artifacts** section. This is a debug APK for installation and testing, not a Play Store release. GitHub's emulator cannot validate BLE/Wi-Fi interoperability on physical radios, OEM behavior, battery use, or live audio quality. A production release still requires the separate security, signing, legal, and device-validation gates below.

## Release signing gate

Debug builds do not require signing secrets. Release packaging and signing tasks (`assembleRelease`, `bundleRelease`, and their package/sign tasks) depend on a fail-closed validation step. Supply these values through the local shell environment or a secrets manager; do not store them in Gradle files, committed properties files, or source control:

- `MESHNET_RELEASE_STORE_FILE`: absolute path to the release keystore.
- `MESHNET_RELEASE_STORE_PASSWORD`: keystore password.
- `MESHNET_RELEASE_KEY_ALIAS`: signing key alias.
- `MESHNET_RELEASE_KEY_PASSWORD`: signing key password.

Create and back up the keystore securely outside the repository. Use `keytool -genkeypair` to create an RSA signing key in a private directory, then set the four environment variables before running `gradle bundleRelease`. Release packaging stops with an actionable error when any variable is missing or the keystore path does not exist. Never commit or share the signing key or passwords.

## Security and delivery boundaries

- “Queued” means accepted into this device's encrypted-frame outbox. A successful GATT write only means the local BLE stack accepted a chunk; it does **not** prove remote application delivery. A directed message is retired only when a receipt from its exact destination passes the configured identity/signature and destination validator. Broadcast ACKs fail closed and do not clear broadcast messages. The outbox holds up to 6,000 frames and applies back-pressure rather than silently evicting an unacknowledged message; queued-frame and replay-record cleanup uses a 30-day age bound. Receipt ACKs have no ACK-of-ACK: after at least one connected BLE, Wi-Fi Direct or Wi-Fi Aware transport accepts the ACK into a local write queue, it is retired locally and can be regenerated if the original message is received again. This is best-effort transport behavior, not an end-to-end delivery guarantee.
- Protocol v6 binds each node ID to a per-install P-256 public key and signs the plaintext digest; receivers verify the device-origin signature before accepting a frame. Relays update authenticated route metadata and re-encrypt with the shared group key. A group-key holder can still alter shared-key-protected hop metadata, so those hops are not treated as proof of a route. All participating phones must use the same protocol version; migration clears incompatible queued ciphertext and replay IDs. The outbox and received-ID cache are local SQLite data. Group credentials are encrypted using an Android Keystore key; losing or resetting that key makes the saved credential unreadable and requires entering the group passphrase again.
- The shared passphrase is a temporary group-key bootstrap, not Signal Protocol. P-256 signatures authenticate a device key, but there is no owner-controlled enrollment, fingerprint approval or revocation UI; a key's cryptographic identity is not proof that its holder is trusted. Group traffic is encrypted with a shared key, so group members can read the same group payloads. There is no per-device session encryption, ratchet, forward secrecy or secure multi-device key rotation. vodozemac is only a candidate and is not integrated into the Android runtime.
- File transfer is limited to 10 MiB per file and two concurrent inbound transfers. The sender reads the selected source in bounded streaming passes and sends a 16-chunk window at a time. The receiver syncs data and writes a compact checkpoint before acknowledging each eight-chunk batch. The terminal ACK is withheld until SHA-256 verification succeeds, the verified file is renamed to its final private destination, and its durable completion/deduplication marker is published. Interrupted sends can be resumed by reselecting the same file with the same filename; the sender reuses its transfer ID and the receiver resumes from persisted checkpoints, including after process recreation. The Android document picker read grant is persisted when the provider offers a persistable permission; reselect the file if its provider revokes access. **Cancel outgoing file transfer** interrupts local sender workers, rotates the sender's persisted transfer ID for a later retry, and sends a best-effort authenticated cancellation command. Receivers persist a 24-hour cancellation tombstone so delayed manifests already queued in an outbox cannot recreate a cancelled partial transfer. Chunks already queued in the sender outbox cannot be recalled and may remain until acknowledged or expired. Chunks received before their manifest are ignored and must be retransmitted by the sender. Partial receiver files expire after 24 hours. Completed files and their deduplication markers are retained in a bounded inbox of 50 files / 100 MiB; oldest completed items are removed when new files need space. **Save received file** exports a completed inbox item through Android's document picker, including when the mesh service is stopped. This is capped, resumable streaming—not an unlimited transfer service.
- Voice notes are locally recorded AAC/M4A clips capped at seven seconds and transferred as encrypted files; the app can play the latest received M4A note. Live voice is a separate best-effort group feature: it uses a shared group key, broadcasts audio to group members, has no individual recipient authorization, no retransmission/ACK, and may lose audio under congestion or radio loss. Incoming invitations expire after five minutes, stale speaker decoders are released after inactivity, and up to eight active speaker streams are mixed.
- A public Internet gateway/NAT, hotspot metering and receiver-measured billing, SPL-token or mainnet settlement, escrow UI/transaction integration, production-grade per-device session cryptography, and iOS are not implemented. Wi-Fi Direct, Wi-Fi Aware, live voice, wallet authorization and file transfer remain hardware-dependent prototypes and have not been validated across physical devices. The Anchor escrow program is not compiled, tested, deployed or audited.
- Android may stop a foreground service under exceptional resource or policy conditions. BLE peripheral advertising and concurrent GATT connections vary by chipset and vendor.
- Pull-request CI builds and signature-verifies the debug APK and runs the focused API 36 Android regression suite; the complete instrumentation suite is manual-dispatch only. Consult the latest run for the authoritative result. Emulator tests do not validate physical Bluetooth/Wi-Fi radios, OEM behavior, battery use or live-audio quality. Do not use this prototype for sensitive or financial traffic before independent security review and physical-device testing.



**Group-delivery boundary:** MeshNet now stores signed local JOIN/LEAVE events, exchanges membership history over best-effort v6 ephemeral frames, and persists local signed recipient snapshots and per-member receipt evidence. These primitives are not yet bound atomically to the original message or integrated into the router/outbox/UI; membership-sync cursors are in-memory and do not resume after process death, and local rosters are not globally authoritative. Group-broadcast ACK therefore remains fail-closed. No message can be represented as delivered to every group member or every offline member. File-transfer checkpoints describe one receiver's persisted chunk progress, not distribution to the whole group.
